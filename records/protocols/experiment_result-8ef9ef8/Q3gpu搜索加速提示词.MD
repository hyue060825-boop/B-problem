
# 补充执行提示词：Q3 多 GPU 离线搜索与批量模拟加速

请在《Codex执行提示词_最新版_Q3多卡同步单模型.MD》的基础上，落实下面的补充要求。此文件是给执行 Codex 的增量任务，不是在声称当前仓库已经具备这些能力。

## 1. 补充目标与优先级

我的算力充足，希望离线搜索教师也实质性使用多张 GPU，提高生成高质量教师标签的效率。

原提示词中“CPU worker 推进环境和几何；各 rank 可在所属 GPU 对多个待决策状态批量推理”的安排，升级为以下要求：

1. 离线搜索默认使用单机四张可用 GPU，设备列表可配置，支持扩展到八张。
2. 必须实现跨卡搜索任务分配和每卡批量策略推理。
3. 必须实现并实际接入 Q3 的 GPU 批量数值模拟核心，以及假设场景与公开历史的批量数值一致性检查。不能只把模型移到 CUDA，环境计算仍全部逐条运行在 CPU，却宣称已完成 GPU 搜索改造。
4. 动态几何、精确证书和不适合张量化的控制逻辑允许保留 CPU；必须记录其耗时和回退比例。
5. 全部搜索数据服务于同一个学生模型；SFT、每轮 DAgger 的监督更新、PPO 继续使用多卡 DDP 同步训练同一个模型。
6. 统一 checkpoint 与 best.pt 的语义不变：只在同一联合训练轨迹的不同时点选优，禁止多卡独立训练不同模型后择优。

本文件替换原提示词第 9.9 节关于搜索仅可选 GPU 推理的安排，并补充第 5、6、9.6、10 节；原文件的信息边界、数据隔离、几何正确性、训练目标及验收门槛继续有效。

先完成代码、正确性验证和吞吐分析，再按原文件的阶段预算运行。不要因本文件提到更多并行分支就自动扩大训练集、搜索深度或总计算预算。

## 2. 执行前核查

先阅读实际仓库、相关 AGENTS.md、原提示词和当前配置，确认分支、提交、模型结构、环境语义及可恢复训练状态。不要将历史审查的结论直接当成当前代码事实。

记录 GPU 型号、可用设备与显存、CPU 核数、内存、PyTorch/CUDA 版本，以及已有任务占用。只使用可用卡组，不停止其他任务、不抢占正在使用的显存。

若当前无法使用四张 GPU，继续完成实现及可执行的验证，保存单卡或 CPU 对照证据，并明确列出尚未完成的四卡验收。不得用模拟设备、四个 CPU 进程或单卡测试冒充四卡成功，也不得静默改成独立模型训练。

## 3. 搜索与训练使用两种不同的并行方式

### 3.1 搜索阶段：一个冻结策略，多卡处理不同任务

每张 GPU 加载同一个 policy_version、同一个参数哈希的冻结策略副本，仅用于推理，不建立独立 optimizer，不进行独立学习。

优先按公开根状态分配任务，使同一状态的候选和假设场景尽量在同一张卡内完成比较。必要时才跨卡拆分大任务，并由统一聚合器合并其充分统计量。

搜索阶段不要求使用 DDP 的梯度同步，也不要为了形式统一而给推理路径添加无用 collective。允许每卡一个搜索服务进程，配合受总 CPU 预算约束的工作进程。

各卡可以保存标签分片和进度日志，全部登记到同一 run 的数据清单。只读模型副本和标签分片不是四个独立训练的 checkpoint。

### 3.2 训练阶段：多卡同步更新一个学生

完成并提交当前轮标签后，冻结数据清单版本，再启动或恢复原方案的 DDP 训练阶段。所有 rank 使用相同模型初始化和共同更新计数，汇总各自数据上的梯度。

只有 rank 0 原子写入统一 latest.pt、best.pt 和全局状态。后续 DAgger 搜索使用本条联合训练轨迹的新版本。

默认搜索与训练分阶段复用同一卡组。暂不实现搜索、训练同时竞争同一 GPU 的复杂流水线；每一轮搜索期间模型版本固定，不在分支中途换权重。

## 4. 将搜索组织成批次

初版仍采用原方案的“一步候选动作 + 固定公开策略后续 rollout”。不要为了 GPU 加速直接换成全知搜索或复杂 MCTS。

一条模拟分支具有稳定身份：

```text
branch_id = (root_state_id, candidate_id, hypothesis_id, replicate_id)
```

同一根状态的不同候选使用相同的相容假设场景集合；候选分支间的可变状态完全隔离。同一个场景中的固定误差机制不能因候选、GPU 编号或批次位置改变。

并行维度来自多个根状态、候选动作和假设场景。将当前活跃分支合并为批次，每推进一步，批量计算数值响应、构造公开特征、执行策略推理，再更新活跃分支。

例如 64 个根状态、每状态 6 个候选、每候选 32 个假设场景，对应 12,288 条待评估分支。这仅解释并行维度，不是默认搜索预算，也不要求这些分支一次全部驻留显存。

原方案的初始假设数量和候选预算保持不变，通过合并多个根状态获得足够批量。参数增加必须有搜索质量和成本证据。

### 4.1 批量执行的必要细节

- 使用 source_exists、channel_mask、candidate_mask、active_mask 等显式掩码处理不同源数、候选数和分支长度。
- 已结束分支不再累计时间、执行动作或产生观测；压缩活跃批次后保留 branch_id 映射。
- 按候选数量或操作类型适当分桶，减少填充与分支分歧；不得通过丢弃长回合和失败分支提高吞吐数字。
- 有效状态必须至少保留一个合法动作，不能让全无效 mask 产生 NaN。
- 宏动作若包含多次测量、频道切换或提前结束条件，应按原语义展开；不能把一个宏动作粗略当成一次观测。
- 根状态和候选数量不足时允许小批次执行；动态合批设置最大等待时间，不为凑批无限阻塞。
- 随机流按稳定任务身份生成，不依赖 worker、rank、批次排序或完成先后。相同配置重分片时应能复现假设场景身份。

## 5. 必须接入的 GPU 数值核心

基于实际 Q3 规则实现批量接口，以下名称只是建议，允许复用合理的现有模块。

### 5.1 Q3TensorKernel

用 GPU 张量实现搜索需要的数值操作，包括：

- 机器人与假设源之间的距离、方位及相关边界判断。
- Q3 信号接收、无信号、近距离反馈，以及实际使用的固定示向误差机制。
- 移动、频道切换、测量、清除成功与失败的状态更新和虚拟耗时。
- 假设场景中的清除状态、任务预算及明确的终止状态。

源坐标等假设真值驻留模拟器内部；策略和候选生成器只获得公开反馈。不要把假设源坐标拼进 actor 特征以减少几何计算。

以当前参考模拟器为语义依据，核对坐标格式、舍入、边界包含关系、动作计时和返回字段。原模拟器中的 Decimal 运算不能未经验证就全部换成 float32。

不得假设退出证书只需检查假设场景中的源已清除。策略的合法退出仍由公开控制器状态及证书判断；评价器可以独立使用模拟真值统计完成情况。

### 5.2 BatchedHistoryConsistency

对多个待接受的假设场景，批量重放或核对公开历史中的数值约束，至少覆盖正观测、无信号、近距离反馈、清除反馈与固定误差一致性。

GPU 可以加速数值筛选；源数、频道唯一性、已清除状态和历史演化等全局约束也必须验证，不能因距离检查通过就宣称场景相容。

约束场景的提议采样器可以先保留 CPU，但它调用上述批量检查，并记录提议数、接受率、CPU/GPU 时间及失败原因。若已有粒子模块，优先复用其合法数值操作，不为满足本补充强行重建整套 belief。

### 5.3 BatchedPolicyEvaluator

每卡使用冻结模型、eval 模式及 inference_mode 执行批量前向。保持实际训练和部署的特征语义、动作 mask 与候选索引一致。

初版用可靠精度建立对照，再试验混合精度；低精度推理与几何数值精度独立配置。记录其对 logits、动作选择及教师标签的影响，不以显存节省替代正确性验收。

策略评估必须接入真实搜索链路。单独跑一个 GPU 矩阵乘法、未使用的批量模型函数或脱离搜索的 demo 不算完成。

## 6. CPU/GPU 边界与精度

CPU 初期保留复杂非凸可行域操作、必要的精确几何证书、动态候选结构和任务调度。这是明确的混合架构，不要求把全部算法一次性迁移到 GPU。

不过，GPU 批量数值核心必须成为已支持操作的默认搜索路径；如果实际大部分操作都落回 CPU，要披露比例并定位原因。

尽量让分支的数值状态常驻显存，批量传递 CPU 几何层真正需要的公开反馈。避免逐分支调用 .item()、逐条主机设备复制或对每一步无条件全设备同步。

使用连续缓冲区、适度的 pinned memory、合批和复用减少开销，所有优化以测量为依据，不默认它们在本项目中必然有效。

### 6.1 边界与回退

针对接收半径、近距离、清除半径、角度跨越正负 pi、重合位置及时间预算临界值建立专门对照。

当浮点误差可能改变离散响应或证书结论时，采用经验证的高精度路径、保守区间或参考实现回退。阈值必须根据实际误差分析和测试确定，不能随意加一个 epsilon 就宣称正确。

若 GPU 仅进行近似预筛，要显式标记近似结果。所有进入最终比较的候选，应在同一组假设场景下用可靠路径复核；不能只复核粗排第一名后宣称它优于所有候选。对被近似筛掉的候选做审计抽样，衡量遗漏风险。

保留原策略首选动作及必要进展动作参与比较。结果无法可靠区分或验证时，标记标签不确定并回退，不硬造唯一最优动作。

性能报告必须计入精确回退和复核耗时。

## 7. 信息条件与评价目标不变

实际训练场景的隐藏坐标、源数、半径、误差场和 seed 不得用于主要教师选择动作。假设场景由公开历史、公开规则和独立随机种子生成。

假设世界的模拟器可以持有该假设的真值；后续策略、几何控制器和候选器只能获得公开反馈。所有相同公开历史下的行为必须满足原提示词的非预知要求。

禁止对每个假设世界分别求全知最优路线，再把这些值平均当成可部署策略的动作价值。

按原方案先比较任务完成可靠性，再比较可比的完整任务耗时。预算耗尽、失败、GPU 异常和搜索截断分别记录，不得把未完成的短轨迹计成快速完成。

有限搜索得到的是预算内的估计改进或当前最好已知动作。除非有独立的最优性证明，不标为“全局最优标准答案”。

## 8. 跨卡任务、数据与恢复

采用有界任务队列或可恢复任务清单，优先按根状态分配工作，减少通信和候选归并复杂度。支持动态领取任务，避免长分支使某张卡长期拖尾。

每条记录保存 root_state_id、branch_id、假设场景哈希、模型版本、搜索参数、完成状态及必要的数值后端信息。

分片采用临时写入后原子提交；全局清单按任务身份去重。部分完成的根状态不能当成完整标签，恢复时补齐或重跑，并拒绝跨模型版本合并。

搜索 worker 失败时，保存已提交数据并重新分配未完成任务；若出现语义错误、非有限值或版本不一致，停止当前阶段并交付错误证据。

断点恢复至少验证一次。恢复后的任务不得重复计入有效标签数；随机流不能因为任务换了 GPU 而重新生成另一套假设场景。

## 9. 正确性验收

在保持原文件测试要求的基础上，补充以下有实际意义的验证：

1. 单步对照：对正常场景及边界场景，比较 CPU 参考与 GPU 核心的公开响应、离散事件、清除状态和虚拟耗时。明确连续数值容差，离散结果不一致必须解释并修复或可靠回退。
2. 完整分支对照：使用相同根状态、假设场景、动作与随机流，逐步重放整条轨迹，定位首次分歧，不能只比较最后总时间。
3. 策略对照：先用相同预定动作隔离模拟器误差，再比较 CPU/GPU 策略闭环。对接近打平的 logits 定义稳定处理，区分推理误差与环境误差。
4. 分支隔离：一个候选的移动、清除、时钟及历史不影响其他候选；掩码、批次压缩、分桶和重排不改变任务身份。
5. 信息隔离：固定公开历史与教师随机种子，替换实际隐藏场景，主要教师输出保持一致。
6. 搜索标签对照：固定同一任务清单，比较 CPU、单 GPU 和四 GPU 的完成统计、候选成本、软标签与推荐动作；统计打平和不确定标签，不仅检查文件存在。
7. 恢复对照：中断后恢复，与未中断运行比较任务完整性、去重、版本和结果。

功能测试可以先用小批次，但实际四卡验收必须使用真实搜索工作负载。没有四卡条件时明确报告未执行。

## 10. 性能验收与报告

用同一冻结策略、同一根状态清单、同一候选集合、同一假设场景、相同展开预算及相同精度约定，对照以下路径：

| 路径                                      | 目的                               |
| ----------------------------------------- | ---------------------------------- |
| CPU 参考搜索                              | 建立可复现基准，合理配置线程和进程 |
| CPU 环境 + 单 GPU 批量推理                | 测量单独批量推理的收益             |
| 单 GPU 批量数值核心 + 批量推理 + CPU 几何 | 测量数值模拟迁移的收益             |
| 四 GPU 搜索，共同数据清单                 | 测量多卡整体吞吐及调度效率         |

完整对照不允许通过减少假设场景、缩短 rollout、删掉失败分支、关闭复核或减少候选来获得“提速”。若比较近似方案，单列其质量变化，不混入等价加速。

固定工作量测量单卡和四卡总耗时，另可报告扩大工作量后的吞吐。不要把四卡完成四倍工作所需时间与单卡原工作时间混为强缩放加速。

记录：

- 完整搜索分支数/秒、有效教师标签数/秒、根状态完成数。
- 单状态耗时的中位数和 P95，初始化时间与稳定运行时间。
- CPU 几何、假设生成、GPU 数值模拟、推理、设备传输、等待、精确复核和写盘开销。
- 每卡批量大小分布、活跃分支数、显存峰值、利用率和负载不均衡。
- 标签接受率、精确回退率、搜索失败/超时比例，以及教师相对当前模型的估计改进。
- 实际硬件、总 CPU 资源配额、代码版本和完整配置。

GPU 计时使用正确的事件或在测量边界同步，避免只量到异步提交时间。区分可能重叠的阶段，不能将重叠耗时简单相加冒充总耗时。

先做预热，再在可控工作量下重复测量并报告波动。至少交付一组四卡端到端记录；小矩阵 microbenchmark 或看到四张卡都有进程不能替代。

不预设四卡必然四倍提速。若未观察到稳定收益，继续根据测量处理小批次、传输频繁、CPU 几何瓶颈、误差回退过多或负载不均衡，并复测受影响路径。

最终仍无收益时，明确区分“功能已实现”“加速收益未证实”，保留证据和可恢复进度。不要为追求显卡利用率扩大无效搜索，也不要擅自改成四个独立学生模型。

## 12. 执行顺序与完成标准

按“核查现状与基线 → 批量策略推理 → Q3 GPU 数值核心与历史一致性检查 → 数值/完整轨迹对照 → 四卡搜索调度 → 固定工作量性能对照 → 小规模标签质量验证 → 接入原方案的四卡联合训练”推进。
