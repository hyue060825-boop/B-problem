## 5. 合并中需做的必要适配

1. **运行版本。** 47 个来源运行文件中，37 个与 main 对应文件完全相同；其余包括路径差异，以及旧版客户端响应、协议深度和轨迹检查。保留 main 的加强实现；最终部署和严格复现入口显式使用冻结运行时，不关闭哈希检查来迁就路径变更。
2. **路径与输出。** 将活动脚本中的 `runs/`、`paper/` 和服务器绝对路径改为新资产入口或显式参数。`build_paper_catalog.py` 改为 handoff 生成入口；原 `organize_paper_branch.py` 不在 main 执行。保留原始配置与 provenance，只在新的活动配置和适配记录中写入新路径。
3. **可复现入口。** `report_deadline_pair.py`、`report_q4_absence_tail.py` 尚有服务器绝对路径；打包脚本默认输出已存在，需支持新输出目录。新评测显式指定新种子，避免沿用入口默认的历史种子区间；原实验记录不改写。
4. **来源标注。** 当前 Q3 主表的父模型行把 evidence 写成候选数据文件。数值复算正确；新生成的表应分别列出父/最终来源，配对表同时记录两侧。历史“final/best/推荐”按当时语境保留，由统一身份清单解释。
5. **文档导航。** 更新 README、AGENTS、GitHub 速查、实现索引、实验/结果入口、Q3/Q4 handoff 和版本索引；保留 Q1/Q2 的有效说明与 LIT-Q2-01。向论文手给出主稿所用旧批次与本次最终批次对照，避免重复写整套说明。

这些适配用于接收和复现，不变更最终策略、权重或原始实验结论。

## 6. 执行顺序与完成条件

直接合并预演产生 3784 个未解决路径，主要为双方独立搬迁造成的 rename/delete、rename/rename；实际内容冲突集中于 README、忽略规则和部署入口。因此采用“main 底稿 + 逐项资产映射”的整合方式。

1. 固定双方提交，在临时本地整合分支构造目标树；辅助目录放在 `projects/competition/.local/B-problem-archive/`，不新增平行工作仓库到 competition 根目录。
2. 按落位表接收原件、档案、权重和部署包，再完成路径、配置、测试及文档适配。为复用、压缩包成员、整合说明和保留的 main 实现分别记录处理方式。
3. 验证原题、main 论文、LIT-Q2-01 和旧结果未被覆盖；核对两份最终模型与冻结运行时、全部分卷和资产去向；复算主表、检查当前链接、运行相称回归与少量最终入口测试。归档数据不原地重生成。
4. 完成一份可审阅的本地整合提交，保留 main 与本次来源分支的双亲关系，不重写共享历史。推送前再核对远端增量，按后续授权同步远端。
